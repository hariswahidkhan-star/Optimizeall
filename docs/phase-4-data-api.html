Two kinds of enumeration, deliberately

Business enumerations become lookup tables in config — platforms, objectives, brands, activity types, content types, outcomes, lead segments, organisation types, template codes, funnel stages. They are the workbook's Lists sheet, carrying the attributes it holds beside each value: the platform's area, priority, value rank, country strength and deduplication rule. Foreign keys to these give the platform what the spreadsheet never had — a value invisible to reporting cannot be selected, which is the workbook's worst structural defect fixed at schema level.

State machines become native PostgreSQL enums — task_state, approval_state, external_action_state, content_status, outreach_state. These are coupled to code, so the migration friction of a native enum is a feature: adding a value should require thinking about who handles it.

Row-level security

enabled and forced on every table carrying org_id
ALTER TABLE pipeline.lead ENABLE ROW LEVEL SECURITY;
ALTER TABLE pipeline.lead FORCE  ROW LEVEL SECURITY;

CREATE POLICY org_isolation ON pipeline.lead
  USING      (org_id = current_setting('app.org_id', true)::uuid)
  WITH CHECK (org_id = current_setting('app.org_id', true)::uuid);

FORCE matters: without it the table owner bypasses the policy, and the application's migration role is usually the owner. app.org_id is set per connection from the authenticated principal's claims and never from a request body.

02

Invariants as Constraints

This is the point of Phase 4. The workbook's rules have been requirements since Phase 1 and architecture since Phase 2; here they become things the database will not permit. A rule enforced in application code is a rule one bug away from being unenforced.

The strongest instrument is the generated column. FR-022 says the lead score is computed, never written. A generated column makes that literally true — there is no UPDATE that can set it, from any code path, including a mistaken migration.

pipeline.lead — the generated columns
score integer GENERATED ALWAYS AS
  (COALESCE(icp_fit,0) * 12 + COALESCE(intent,0) * 8) STORED,

band text GENERATED ALWAYS AS (
  CASE WHEN icp_fit IS NULL AND intent IS NULL THEN NULL
       WHEN COALESCE(icp_fit,0)*12 + COALESCE(intent,0)*8 >= 80 THEN 'A'
       WHEN COALESCE(icp_fit,0)*12 + COALESCE(intent,0)*8 >= 60 THEN 'B'
       WHEN COALESCE(icp_fit,0)*12 + COALESCE(intent,0)*8 >= 40 THEN 'C'
       ELSE 'D' END) STORED,

funnel_stage_code text GENERATED ALWAYS AS (
  CASE
    WHEN outcome_code = 'Converted'           THEN '8_won'
    WHEN outcome_code = 'Application Started' THEN '7_opportunity'
    WHEN outcome_code = 'Meeting Booked'      THEN '6_meeting'
    WHEN outcome_code IN ('Interested','Info Requested') THEN '5_interested'
    WHEN outcome_code IN ('Declined','Not Relevant',
                          'Do Not Contact / Unsubscribed') THEN '9_closed_lost'
    WHEN message_sent    THEN '4_contacted'
    WHEN accepted        THEN '2_engaged'
    WHEN connection_sent THEN '1_awareness'
    WHEN COALESCE(icp_fit,0)*12 + COALESCE(intent,0)*8 >= 60 THEN '3_qualified'
    ELSE '1_awareness'
  END) STORED,

CONSTRAINT converted_needs_order_ref
  CHECK (converted_at IS NULL OR pci_order_ref IS NOT NULL),
CONSTRAINT accepted_needs_request
  CHECK (NOT accepted OR connection_sent)

A generated column must depend only on columns in its own row, so the four outreach facts — connection_sent, accepted, message_sent, outcome_code — are denormalised onto the lead by the aggregate as they occur. That is a deliberate trade: a small amount of duplication buys a derivation that cannot drift from its definition.

approval.approval_item — four eyes at the schema level
CONSTRAINT four_eyes CHECK (
  decided_by IS NULL
  OR (decided_by <> generating_actor_id
      AND (reviewing_actor_id IS NULL OR decided_by <> reviewing_actor_id))
)
-- plus a trigger rejecting any decided_by whose actor_type <> 'human'

Generator, reviewer and approver are three distinct principals, and the constraint refuses any row where they are not. “The AI approved its own work” is not a bug that can occur — it is a row the database will not accept.

content.message_template — closing an open item in the workbook itself
CONSTRAINT approved_needs_approver
  CHECK (status <> 'approved'
         OR (approved_by IS NOT NULL AND approved_at IS NOT NULL))

The workbook's message templates are currently marked Approved with no approver recorded — an open item its own changelog flags. Here that state cannot exist.

Lineage & Audit

“Every KPI exposes lineage” has been a requirement since Phase 1 and a principle since Phase 3. It is a table.

audit.audit_event — append-only, hash-chained per organisation
CREATE TABLE audit.audit_event (
  id             uuid NOT NULL,
  org_id         uuid NOT NULL,
  seq            bigint NOT NULL,
  prev_hash      bytea  NOT NULL,          -- chain to the predecessor
  payload_hash   bytea  NOT NULL,
  occurred_at    timestamptz NOT NULL DEFAULT now(),
  actor_id       uuid NOT NULL,
  actor_type     identity.actor_type NOT NULL,
  agent_version_id  uuid,
  prompt_version_id uuid,
  action         text NOT NULL,
  entity_type    text NOT NULL,
  entity_id      uuid,
  correlation_id uuid NOT NULL,
  risk_level     text,
  result         text NOT NULL,
  cost_amount    numeric(18,6),
  payload        jsonb NOT NULL,
  PRIMARY KEY (id, occurred_at),
  UNIQUE (org_id, seq, occurred_at)
) PARTITION BY RANGE (occurred_at);

REVOKE UPDATE, DELETE ON audit.audit_event FROM app_role;

The REVOKE is the important line. Tamper-evidence from the hash chain is worth little if the application role can rewrite history; here it cannot, and a daily anchor written to object storage makes any gap detectable.

Indexes & Partitioning

CREATE INDEX lead_stage_idx      ON pipeline.lead (org_id, funnel_stage_code, updated_at DESC);
CREATE INDEX lead_band_score_idx ON pipeline.lead (org_id, band, score DESC)
  WHERE qualified AND declined_at IS NULL;
CREATE INDEX outreach_followup_idx ON pipeline.outreach_item (org_id, sent_at)
  WHERE state IN ('awaiting_reply','follow_up_1');
CREATE INDEX approval_queue_idx  ON approval.approval_item (org_id, state, expires_at)
  WHERE state = 'pending_human';
CREATE INDEX content_pub_idx     ON content.content_item (org_id, status, published_at DESC);
CREATE INDEX task_queue_idx      ON worksurface.task (org_id, state, priority, scheduled_at);
CREATE INDEX audit_corr_idx      ON audit.audit_event (org_id, correlation_id);
CREATE INDEX outbox_unpublished  ON messaging.outbox (occurred_at) WHERE published_at IS NULL;
CREATE INDEX chunk_ann_idx       ON knowledge.chunk
  USING hnsw (embedding vector_cosine_ops) WHERE superseded_at IS NULL;

Three of these are partial, and deliberately so. The approval queue is only ever queried in one state; the follow-up sweep only cares about two; the outbox relay has exactly one query. A partial index on the state anyone actually asks about is a fraction of the size and stays in memory. The vector index excludes superseded chunks so retrieval never filters them out after the fact.

Migration Strategy

No release contains a change that requires the previous release to be down. Every structural change is expand → migrate → contract, spanning at least two releases.

PhaseWhat shipsRule
ExpandNew column nullable, new table, new index CONCURRENTLYOld code still works unchanged
MigrateIdempotent, batched, resumable backfill run as a job — never inside the migrationBatches of ~5,000 rows with bounded lock time
ContractSET NOT NULL; constraints added NOT VALID then VALIDATE; old column droppedOnly after the release that stopped reading it is live
  • Adding a CHECK constraint takes a strong lock — add it NOT VALID, then VALIDATE CONSTRAINT, which takes a weaker one.
  • Indexes are always built CONCURRENTLY; a failed concurrent build leaves an invalid index the next migration must drop.
  • Enum values can be added but not removed; removal is a new type plus a rewrite, planned across two releases.
Seed data is not migration data

The workbook's content — 133 platforms, 11 objectives, 7 brands, 5 domains, 15 templates, 15 compliance checks, 63 tasks, 7 pillars, 76 keywords, 5,683 briefs, the KPI catalogue — loads through the governed import path, not through migration scripts. It is business configuration: it must be diffable, approvable and audited, and a migration script is none of those. Only the enumerations that code depends on structurally ship as migrations.

Rollback. Every migration declares a down path or is explicitly marked irreversible with a reason, and irreversible migrations require approval before merge. In practice forward-fix is preferred — and the expand/contract discipline is exactly what makes forward-fix possible without downtime.

StatusUsed forNever used for
400Malformed syntaxBusiness-rule failure
403Authenticated but not permitted — names the missing permissionHiding the existence of a record
404Not found or not visible to this organisation — deliberately indistinguishable—
409State conflict, e.g. approving an already-decided itemOptimistic-concurrency failure
412If-Match mismatch — someone else changed the row—

The line between 400 and 422 carries weight: a client can retry a 400 after fixing the payload, but a 422 means the platform's rules rejected the intent — and the correct response is usually to change the plan, not the JSON.

Idempotency, at two levels

  • Same key, same body → the stored response is replayed with Idempotency-Replayed: true.
  • Same key, different body → 422 type: idempotency-key-reuse. Silently accepting it is how duplicate posts happen.
  • Endpoints causing external effects additionally reserve an external_action row before the connector runs. The API key protects against duplicate requests; the ledger protects against duplicate effects. They are not the same problem, and solving only one of them leaves the failure that matters.

The agent token is the mechanism behind scope binding. Because it is minted per task and carries the task id, the gate can verify that every entity a tool request references lies inside that task's scope graph — without trusting anything the model asserted. An agent prompt-injected into requesting an action against an unrelated entity fails there, before policy, because the token cannot address it.

Inbound webhooks

receive → verify signature and timestamp window
        → persist raw body to object storage
        → INSERT webhook_event  (unique on org + connector + provider_event_id)
        → 200 within 500 ms
        → enqueue normalisation asynchronously

Five properties, each earning its place: signature verified before anything is persisted, so a replayed event never enters the system; the raw body kept, so a normalisation bug found three weeks later can be replayed against the original; deduplicated on the provider's event id, because at-least-once delivery is the norm; acknowledged fast, with no AI work inside the handler; and processed through the same queue classes as everything else, so a webhook flood cannot starve interactive work.

Outbound webhooks are not in v1 scope, but the contract is reserved now — HMAC-SHA256 over the raw body with a timestamped signature header, exponential retry over 24 hours, per-subscription dead-lettering — so adding it later is additive rather than a redesign.

Queues, Caching & Vectors

Six queue classes as separate Temporal task queues — separation, not priority numbers, is what prevents starvation
QueueCarriesConcurrencyRationale
criticalEmergency stop propagation, kill-switch checks, security alerts8Must never queue behind anything
standardPlanning, drafting, QA, compliance, scoring16The bulk of the work
researchWeb research, competitor scans, answer-engine audits6Slow and bursty; isolating it stops one 90-second fetch blocking a draft
external-writePublishing, sending, CRM writes4Deliberately narrow. External writes are rate-limited by the provider; more concurrency buys nothing but 429s
approval-dependentWork resuming after a human decision8Bursty — a manager clearing twelve approvals should not stall the standard queue
retryBackoff re-attempts4Isolated so a failing integration cannot consume the standard pool

Workflow timers — the day-4 and day-10 follow-ups, approval expiry, the 30-day indexation gate — are Temporal timers, not queue entries. They cost nothing while waiting and survive restarts, which is precisely why the workflow engine exists. When external-write depth exceeds its threshold the platform slows upstream preparation rather than accumulating approved work that cannot be executed; the alternative is a queue of approvals that expire before they are reached.

Caching

The governing rule: cache keys embed a version, so invalidation is unnecessary. A key like agentver:{agent_version_id} addresses immutable content — a new version is a new key, and the old entry expires on its own. Most cache bugs come from invalidation logic, so the design removes the need for it wherever possible.

CachedTTLInvalidation
Agent version + grants · prompt version1 hNone needed — immutable by key
Org config · enumerations1–6 hVersion bump on write
Connector health30 sPub/sub on state change
KPI read models5 minEvent-driven refresh
Idempotency guard · rate-limit buckets24 h · windowExpiry only
Never cached: approval state, external-action state, suppression entries—Each is a decision point where a stale read causes a real-world error — publishing something whose approval was withdrawn, sending twice, or contacting someone who declined
The kill switch — a deliberate exception

It is checked on every tool call, so a database read per call is wasteful — but a stale off value is the dangerous direction. So: Redis-backed with pub/sub invalidation and a two-second maximum staleness, plus an unconditional database read immediately before connector execution. Cheap in the common path, correct in the path that matters.

Vector storage

SourceChunking strategy
Prose documentsStructure-aware: split at headings, then 600–900 tokens with 100-token overlap, never mid-sentence
SpreadsheetsOne chunk per logical row group, carrying the header as context. A 5,683-row brief bank chunked by token count produces fragments that mean nothing; chunked by row it produces 5,683 individually retrievable briefs
PresentationsOne chunk per slide, speaker notes appended
Policies and playbooksOne chunk per numbered technique or rule, so retrieval returns a complete rule rather than half of one
 
filter (org_id via RLS · classification vs agent scope · document ACL · not superseded)
  → ANN search over the surviving set
  → optional rerank of the top 30
  → return top k with citations {document_id, document_version_id, chunk_id, ordinal}

Filter before ANN, never after. Retrieving fifty neighbours and discarding the ones the agent may not see silently degrades recall — and leaks the existence of restricted material through result counts.

Embedding model changes are additive, never in place. embedding_model_key is stored per chunk; changing models means new rows under a new key and a second index, then a cutover. Re-embedding in place makes the index temporarily incoherent, with old and new vectors sharing one space, and there is no way to detect that from the results.

A second embedding serves a different purpose entirely: content_item.embedding powers near-duplicate detection before drafting — one of the three controls standing between the 5,683-brief bank and the thin-content failure mode the workbook itself warns about.
