01

System Architecture

Phase 1 committed to a philosophy: deterministic software owns identity, permissions, schedules, state, budgets, approvals, integrations and audit; AI owns reasoning, research, drafting, classification and bounded recommendation. That philosophy survives contact with an implementation only if one structural decision is made and never softened.

The rule everything else follows from

The agent runtime has no path to any external system and never holds a credential. An agent emits a structured tool request; the platform validates, authorises, policy-checks, approval-checks, rate-limits, deduplicates, executes and audits it. The model proposes; the platform disposes.

If this is ever relaxed, every control specified in Phase 1 becomes unenforceable — a model that can call an external API directly bypasses all of them at once.

Service Boundaries

Five rules make the platform core a modular monolith rather than a large namespace. Break any of them and it becomes a distributed system with none of the benefits and all of the costs.

  1. A module owns its own database schema. No module reads another module's tables — ever, including in reports.
  2. Synchronous cross-module calls go through a published application-service interface, never a repository.
  3. Asynchronous communication is a domain event via the transactional outbox. Consumers are idempotent.
  4. A module's public surface is its interface, its events, and the tools it exposes to the gate. Everything else is internal.
  5. Any module can be extracted into its own service by replacing rule 2 with a network call and rule 3 with a broker — and nothing else changes.

03

The Execution Gate

Every external effect in the system — publishing a post, sending an approved email, writing to the CRM, queueing an outreach item for a person — passes through one pipeline. There is no second path, and building one would be the single change that invalidates this architecture.

04

Agent Architecture

An agent is not a running process, a conversation, or a prompt. It is a versioned configuration record that the runtime instantiates for one task and then discards.

AgentVersion
  ├── identity          agent code (ORCH, LEAD, CWRITE…), version, lifecycle state
  ├── prompt            PromptVersion reference — registry, never source
  ├── model policy      task class → model class, reasoning config, fallback chain
  ├── tool grants       explicit allow-list; deny is the default
  ├── knowledge scope   which collections, which classifications
  ├── memory scope      which of six layers, read/write per layer
  ├── output contract   the JSON Schema the platform validates against
  ├── policies          approval requirements, escalation, confidence threshold
  └── ceilings          max steps, tool calls, wall time, tokens, cost

Four consequences fall out of this, and each is a Phase 1 requirement becoming a property of the design rather than a discipline:

  • Behaviour change is a data change. Adjusting a model, prompt, tool set or limit is a version promotion, not a deployment.
  • Every output is attributable to a version — audit becomes a foreign key, not a logging convention.
  • Rollback is a pointer move. The previous version is still there.
  • An agent cannot grant itself anything. Grants live in identity; the runtime receives an effective permission set it has no means to mutate.

The execution loop

RunAgent is a Temporal activity, not a workflow. The distinction is load-bearing: the workflow owns control flow and durability, the agent owns judgement inside one bounded step. An agent that dies mid-run is retried by the workflow with the same input — it does not resume a half-finished conversation, because there is no conversation to resume.

RunAgent · one bounded step
  1. workerTemporal activity RunAgent(agentVersionId, taskId, input)
  2. runtimeLoad the agent version and its effective grants — cached by version key, never by agent name
  3. runtimeAssemble context: system prompt, campaign brief if the task has one, retrieved knowledge with citations, permitted memory slices, task input
  4. runtimeWrap all external text in untrusted-source envelopes carrying kind, URL and retrieval time
  5. gatewayModel call by task class — never by model name
  6. runtimeValidate the structured output against the contract
  7. runtimeInvalid → regenerate, maximum twice → escalate as TaskFailed. Invalid output never becomes trusted data
  8. gateIf the output contains tool requests, emit them to the gate, await results, append, return to step 5
  9. runtimeCeilings checked every iteration — steps, tool calls, wall time, tokens, cost. On breach: stop, preserve state, log the reason, notify
  10. runtimeReturn structured result with confidence, evidence and recorded cost

Ceilings are enforced in three independent places — the runtime counts steps and tokens, the gateway enforces cost, and the Temporal activity carries a wall-clock timeout — so no single bug removes them.

The rule that makes this affordable and auditable is retrieval, never accumulation. No agent receives unbounded history; a per-version retrieval budget caps chunks and tokens; every retrieved chunk is recorded in the trace with its document version. That is what lets the system answer, six months later, “what did the agent actually know when it wrote this?”

The model gateway

Structured output is the only contract

Every agent declares a JSON Schema, validated before anything becomes trusted application data. The lead-qualification contract is worth showing because of what it omits:

{
  "required": ["lead_ref","qualified","icp_fit","intent","evidence","confidence"],
  "icp_fit":  { "type":"integer", "minimum":1, "maximum":5 },
  "intent":   { "type":"integer", "minimum":1, "maximum":5 },
  "evidence": { "type":"array", "minItems":1,
                "items": { "required":["claim","source","retrieved_at"] } },
  "confidence": { "type":"number", "minimum":0, "maximum":1 },
  "assumptions": [...], "missing_information": [...],
  "additionalProperties": false
}

There is no score field. The agent supplies two judgements with evidence; the platform computes ICP × 12 + Intent × 8 exactly, and derives the funnel stage the same way. A model is never asked to do arithmetic the platform can do exactly. And minItems: 1 on evidence is the schema-level expression of the rule that a rating without evidence is not a valid output — so it cannot be persisted, rather than being caught in review.

Four-eyes, mechanically

“An AI can never approve its own work” is implemented as a predicate on the approval decision, not as a workflow convention:

grant_approval(item, principal) requires
      principal.type == Human
  AND principal.id  != item.generating_principal_id
  AND principal.id  != item.reviewing_principal_id
  AND principal has permission(item.action_type)
  AND item.state == PendingHumanApproval

Generator, reviewer and approver are three distinct principals and the database enforces it. An agent identity cannot satisfy the predicate at all, so the failure mode does not exist rather than being guarded against.

Data Architecture

Architecture, not schema: stores, ownership, aggregates, consistency, lineage, retention and isolation are settled here. Column-level DDL, indexes and migrations are Phase 4.

Storage topology
StoreHoldsWhy here
PostgreSQLAll business state, outbox, audit chain, vector index, read modelsOne transactional boundary makes the outbox, the audit chain and permission-scoped retrieval simple; splitting them makes each a distributed problem
pgvectorKnowledge chunks, content embeddingsRetrieval must join to organisation, permission, document version and classification. In-database that is a WHERE clause

Isolation is structural

CREATE POLICY org_isolation ON <table>
  USING (org_id = current_setting('app.org_id')::uuid);

Every business row carries org_id, and row-level security is on for every table in every module schema. A forgotten WHERE org_id = … returns nothing rather than returning another organisation's data. The session value comes from the authenticated principal's claims, never from a request body. Knowledge retrieval carries the same predicate plus a permission join — so a vector search cannot surface a chunk the requesting agent is not entitled to. Multi-tenancy therefore arrives early at no extra cost.

Cross-aggregate consistency is eventual, via events — never a multi-aggregate transaction. Where a business process spans aggregates, the saga is a Temporal workflow, which is precisely what durable execution is for.

Outbox and idempotent consumption

BEGIN
  … aggregate change …
  INSERT INTO messaging.outbox (org_id, event_type, payload, correlation_id, occurred_at)
COMMIT
                    relay → publish → consumer
consumer: INSERT INTO messaging.processed (consumer, event_id) ON CONFLICT DO NOTHING
          if inserted → handle

The outbox writes in the same transaction as the state change, so an event can never describe a change that did not happen and a change can never fail to emit its event. The processed table makes every consumer idempotent by construction — which is the precondition for making retries free, and therefore for making external writes safe.

The external action ledger

Lineage

KpiObservation ──> Computation ──> formula_version
                        │           window (from, to)
                        └──> input_refs[] → (module, aggregate, id) …

“Every KPI exposes lineage” is a data-model obligation, not a UI feature. Every displayed number drills through to the rows it came from and the formula version used. KPIs are addressed by stable identifier, never by position — the workbook's own worst live defect was a row insert that made the revenue tile display meetings, and a regression test now asserts every tile resolves to its intended KPI. Dashboards read materialised read models refreshed by event handlers, never raw aggregates at request time, which is what makes the p95 target achievable without denormalising the write model.

Classification, retention, erasure

ClassExamplesDefault retention assumed
PublicPublished content, public competitor factsIndefinite
InternalPlans, KPIs, agent traces, evaluation results24 months rolling
ConfidentialProspect and contact personal data, interaction history, consent24 months from last interaction
RestrictedCredential references, Employee Score, HR notesEmployment + statutory period

Erasure is an operation, not a delete: a subject request tombstones the personal data, preserves the audit chain by replacing payloads with hashes, and records the erasure itself as an audit event. Aggregate KPIs computed before erasure stay valid because they never depended on the erased fields. These retention defaults are mine, not PCI's — they are the assumption behind the unanswered prerequisite and must be confirmed by legal before production.

The one design this phase defers

Under the single-region assumption, residency is a deployment property. If PCI later needs a Gulf data boundary — plausible given the Saudi and UAE focus and PDPL — residency becomes a data property: an org-level residency attribute, per-organisation storage routing, and provider eligibility filtered by region. That changes storage topology and isolation, not module boundaries, and it is far cheaper to decide before there is data than after. It is the strongest reason to answer P2-05 early.

Seven layers of authorisation

A request must clear all seven, and every layer is server-side.

#LayerWhat it decides
1Organisation scopeRow-level security — structural, not diligent
2Role permissionRBAC on the operation
3Field-level authorisationComputed and manager-owned fields reject unauthorised writes — replacing the workbook's sheet protection
4Tool grantThe agent's allow-list; deny by default
5Scope bindingTargets must lie in the task's scope graph
6PolicyDeterministic business rules — the Golden Rules and QA checks
7ApprovalA human decision where required

Layers 4 and 5 are what make an agent's authority narrower than its role: even a correctly-permissioned agent cannot act outside the task it was given.

Secrets

Credentials live in the vault; the database holds references — the same discipline the workbook already enforces in its Accounts Register, where only the vault entry name is recorded. The invariant: no secret is ever placed in a prompt, returned to a model, or transmitted to the agent runtime. An agent requests publish_content(content_id); the connector resolves the credential at the moment of execution and discards it. There is no code path by which a model can observe a token, because the process that holds tokens and the process that talks to models are different processes with different network policies.

The kill switch, checked in three places

Emergency stop must catch approved-but-unexecuted items — the case that matters, because an approval granted before a problem was discovered would otherwise still fire. One check would be a single point of failure, so there are three: at the execution gate (step 6), at activity start in the worker, and at approval dispatch — plus a signal to running workflows so they park rather than spin. Release requires the Owner. Granularity: all external writes, one channel, one workflow, or one agent.

Prompt injection — four layers, no single point of trust

LayerControlWhat it stops
IngestionType validation, size limits, scanning, isolated parsing, provenance captureMalicious documents at the door
FramingUntrusted-source envelopes; standing rule that enveloped content is dataNaive instruction-following
CapabilityTool allow-list per agent version; write tools deny-by-defaultAn agent persuaded to act cannot reach a tool it was never granted

Denied invocations are logged with agent, version, tool, matched rule and correlation ID, and repetition raises a security alert. A rising denial rate is treated as a defect in the agent version, not as evidence the policy engine is working well.

Audit integrity

The audit log is append-only and hash-chained per organisation — each event carries the hash of its predecessor, with a daily anchor written to object storage, so tampering is detectable rather than merely discouraged. It records agent, versions, prompt version, trigger, input, retrieved knowledge with document versions, model, output, tool calls, approval, result, error, cost and timestamp. What it deliberately does not record is hidden chain-of-thought: the required rationale — evidence, rules applied, KPIs consulted, sources retrieved, assumptions stated — is reconstructable from recorded inputs and structured outputs, and is more useful in a review than a transcript.

Integration Architecture

Human-assisted connectors are first-class

This is the architectural answer to Phase 1's central constraint, and it is the piece most likely to be under-designed. ISendChannel has two implementations, interchangeable to every layer above.

API channelHuman-assisted channel
QueueReserve ExternalAction, call connectorReserve ExternalAction, create HumanWorkItem

A fourth consequence is planning honesty: human-executed steps are budgeted against human capacity, so the daily plan cannot promise a hundred sends when one person is available.

The connector manifest

ConnectorManifest
  key · display name · area · value rank
  tier                    T1 read+write · T2 read-only · T3 human-assisted · T4 manual · T5 prohibited
  auth · scopes[]         least privilege, listed explicitly
  read_operations[]       operation → normalised entity
  write_operations[]      operation → idempotency strategy → reconciliation query
  restricted_operations[] what this connector must never expose as a tool
  rate_limits[]           per credential, per endpoint, per window
  webhooks                available? signature scheme?
  health_probe            liveness and auth validity
  data_classifications[]  what it may carry
  verified_on · verify_interval        default 6 months

Two fields are unusual and both are load-bearing. restricted_operations names what a connector could do but must not expose — a CRM connector might technically support bulk delete, and declaring it restricted means no tool exists, so no agent can request it and no policy exception can enable it without a manifest change and its approval. verified_on mirrors the workbook's own discipline: every platform fact it records is stamped for six-monthly re-verification. A connector past its date raises a task and degrades write operations to confirmation-required. Acting on an expired platform rule is how a compliant integration silently becomes a terms breach.

Health as a state machine

Connected ──auth error──> AuthenticationExpired ──reauth──> Connected
    │                              │
    ├──429 / quota──> RateLimited ─┘
    ├──error rate > threshold──> Degraded ──recovery probe──> Connected

Agents check health before attempting work, and the orchestrator treats a degraded high-value connector as a planning input rather than a runtime surprise.

Deployment Architecture

Environment isolation is asserted, not assumed

At startup every service asserts that its bound connector implementations match the environment class. A production connector type in a non-production environment fails the health check and the service refuses to serve. That is what turns “test agents cannot contact real audiences” from a hope into a mechanism.

Observability

One correlation_id per business workflow flows request → workflow → activity → agent execution → model call → tool request → connector call → audit event. “Trace one business workflow across services, agents and model calls” therefore becomes a query rather than an inference — which is the difference between an audit requirement that is satisfiable and one that is aspirational.

A

What Phase 2 Does Not Decide

Stated plainly, so nobody builds against something this phase did not settle:

  • No physical schema. Aggregates, invariants, ownership and consistency are fixed; tables, columns, indexes, partitions and migrations are Phase 4.
  • No API contracts. Module interfaces and event names are fixed; routes, request and response schemas, validation, error shapes and idempotency headers are Phase 4.
  • No screens. Phase 3 owns information architecture and wireframes; this document names workspaces only where architecture requires them.
  • No agent prompts. The registry, contracts, ceilings and promotion path are fixed; the prompts themselves are Phase 5.
  • No workflow definitions. The engine, state persistence and six representative flows are fixed; the full catalogue is Phase 6.
  • No residency design beyond a single region — deferred deliberately, and cheap only while there is no data.
