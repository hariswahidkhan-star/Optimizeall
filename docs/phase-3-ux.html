Assumption Carried

P3-02 — who approves, on what device, in what window — is unanswered. Assumption A-06: desktop-first, with full mobile support for approval, notification, dashboard, agent status, daily report and emergency pause.

If approvals in practice happen on a phone between meetings — which the two-hour journalist-request SLA implies — the Approval Inbox becomes a mobile-first design and the desktop layout becomes secondary. That inverts the layout work for one screen and changes nothing else, which is why it was safe to proceed.

The five Phase 2 assumptions still stand. One matters here: if the CMS has no write API, the Content Command Center's publish control becomes a hand-off to the send queue, identical to outreach.

01

What This Product Is

An AI Workforce Command Center — an operations console, not a document system and not a chatbot. Screens here are scanned and operated, not read top to bottom, so the craft is information design first and typography second.

Every design decision below is subordinate to three questions, in this order:

  1. What did the workforce do? — since I last looked, without opening a log.
  2. What needs me? — decisions only I can make, ordered by cost of delay.
  3. What happens next? — today's plan, and whether it is at risk.

A dashboard that answers these badly is a wall of charts. A dashboard that answers them well is short.

Design principles
#PrincipleConsequence
P1Summary before detailEvery workspace opens on state, not on a table. The table is one click down
P2No number without provenanceEvery metric drills to lineage: source → observation → formula → value. A figure that cannot be traced is not displayed
P3State in form, not only colourPills, stripes and icons carry status; colour reinforces. An accessibility requirement that also survives printing
P4Every recommendation shows whyEvidence, rules, KPIs, sources, assumptions — never hidden chain-of-thought
P5Research · draft · recommendation · approval · execution are visually distinctA draft must never look like something that has been sent
P6The target is visible before the actionYou see who receives this, on what channel, before you can approve it
P7Emergency stop is always reachablePersistent in the top bar, two-step confirm, never buried in settings
P8Empty states teachThe workbook starts empty and so does the platform. First-run emptiness explains what will fill it
P9Freshness is statedEvery externally-fed panel shows when that source was last read
P10Agent work is labelled as agent workAttribution to agent and version everywhere a human would otherwise assume a person did it

04

Approval Inbox

The human-in-the-loop requirement is the platform's central control and its most likely bottleneck. This screen has to make careful review fast — because an approval queue that feels slow is one that gets rubber-stamped, and a rubber-stamped queue is worse than no queue at all.

The approval item anatomy — every element is mandatory, on every item
ElementWhy it cannot be optional
Agent · version · prompt versionAttribution, and rollback if a pattern of bad output appears
Proposed action as an effect“Publish to the website”, not “approve content #812”
TargetWho receives this, on what channel — visible before any action is possible
ReasonWhy the agent proposed it now
PreviewExactly what will happen, rendered as it will appear
Risk classificationWith the specific rule that set it
Expected benefitThe KPI it serves
Supporting researchEvidence with sources, retrieval dates and publication dates
Why panelRules, KPIs, knowledge versions, assumptions, missing information
Compliance checksEach named check with its pass state
ExpiryCountdown, and what happens at zero — cancel or regenerate
Four-eyes trailGenerating agent, reviewing agent, and that neither can approve
S-02

Approval Inbox

Purpose
Make the human-in-the-loop requirement fast enough that it does not become the bottleneck the platform is judged by
Primary user
Manager. Secondary: Owner, Compliance
Data
The full item anatomy above, per item; queue grouped by expiry, risk and type; throughput and median decision time
Actions
Approve · Reject · Edit (inline, with a diff against the agent's version) · Request revision. Reject and revision require structured feedback — it is training data for evaluation, so it is not optional
Filters
Type · risk · agent · campaign · brand · objective · expiry window · requires-me-specifically
Search
Within the queue: subject, target, agent
Tables
Queue is a list by default; a table view exists for audit-style review
Cards
The item pane is one composed card; compliance checks are chips
Charts
One — approval throughput and median decision time over 14 days, at the top of the queue, so a growing backlog is visible before it becomes a crisis
Notifications
Push for expiring items; escalation as expiry nears; digest in the daily brief
Empty
“Nothing awaiting your approval”, plus the count decided today and the next scheduled agent run
Error
An approved item that fails to execute returns to the queue marked Execution failed, stating whether the external effect occurred. An item whose target was suppressed after approval is withdrawn automatically with the reason
Loading
Queue skeletons; the item pane loads independently so navigation stays instant
Mobile
Full — the highest-value mobile screen. One item per screen, actions as a fixed bottom bar. Swipe is not bound to approve or reject — a gesture that publishes content or messages a person is the wrong affordance
Permissions
Manager and Owner approve. Compliance may view all and reject on policy grounds but cannot approve. Operator sees only items they generated, read-only. No agent principal can appear as an approver anywhere on this screen

10

Cross-Cutting States

Specified once rather than repeated across twenty-five screens.

Loading — nothing blocks the whole page
CaseTreatment
List or tableSkeleton rows at the final row height so nothing reflows; header, filters and actions render immediately and stay usable
Metric tileLabel and threshold render; the value area is a muted placeholder. The label never moves
ChartAxes, gridlines and legend render; the plot area is muted until data lands
Long agent runProgress by step, not a spinner: “Drafting · step 3 of 6 · 41s”, with cancel
Slow external sourceThe panel renders from cache and marks itself stale rather than blocking
Empty — three genuinely different things, and conflating them is the commonest dashboard failure
KindPatternExample
First runExplains what will appear and what produces it“No content published yet. Once a brief passes QA, compliance and approval, published items and their performance appear here.”
Filtered to nothingStates the filter and offers to clear it“No leads match band A · Gulf · last 7 days. Clear filters”
Nothing, and that is goodConfirms the good state without celebration“Nothing awaiting your approval.” · “Data health: all ten checks read zero.”

“No data” on an empty first run reads as a bug; the same words on a cleared approval queue read as a loss. They are different screens.

Error
KindTreatment
Permission deniedSays what is restricted and who can grant it. Never a blank screen, never a status code
Integration degradedInline banner on the affected panel only, naming the connector, its state and what still works. The rest of the screen keeps functioning
Stale dataFreshness stamp with a marker past the threshold. The number is still shown — hiding it is worse than labelling it
Action failedStates what failed, whether it was retried, whether the external effect happened, and the safe next step. For external writes it always distinguishes “not sent” from “may have sent”
ValidationAt the field, on blur, in business terms: “298 of 300 characters”, not “maxLength exceeded”
Agent failureNames the agent and version, the ceiling breached or the error, that state was preserved, and what the platform did next

Permissions expressed in the interface

  • Actions a role can never perform are absent, not disabled.
  • Actions a role could perform but not right now are disabled with the reason on hover and focus — “Awaiting compliance check”, “Requires a second approver”.
  • Data a role cannot see is absent; the interface never renders a redaction placeholder that reveals the shape of what is hidden.
  • Restricted HR data sits behind an explicit role and never appears in aggregate views a wider audience can reach.

Notifications

In-app first, with connectors architected for email, Slack and Teams; configurable per event. Two rules: an approval nearing expiry escalates, and nothing notifies twice for the same item unless its state changed.

Mobile

Full: Command Center, Approvals, Send Queue, Reports, agent status, emergency pause, notifications. Read-only: most workspaces. Desktop only: workflow editor, Administration, bulk operations, the importer's diff view. On mobile the approval card is the whole screen with actions in a fixed bottom bar within thumb reach — and swipe is not bound to approve or reject.

A

Two Deliberate Refusals

No bulk approve for anything reaching a person or the public

Bulk actions exist for reject, and for internal low-risk item types only. The workbook's entire quality thesis is that personalisation and review are what make outreach work — its benchmarks, its Employee Score, its Golden Rules and its message limits all encode that. A “select all → approve” control would quietly undo it, and would reduce the four-eyes principle to theatre.

This will be asked for, probably within the first month, and probably by whoever is clearing the queue. The answer is no, and the reason is in the workbook rather than in my preference.

No free-form workflow canvas

Phase 2 established that workflow definitions are versioned, tested and owned by the platform. A builder that lets anyone assemble arbitrary graphs at runtime contradicts that directly: it produces untested execution paths with real external effects — publishing, messaging, spending.

S-15 is therefore a visual editor over versioned definitions: a restricted node palette, mandatory validation, a dry-run against sandbox connectors, and a diff plus approval before promotion. Closer to a schema editor than to a drawing canvas. If what is actually wanted is “let a manager change a cadence or a threshold without engineering”, that already exists — it is Settings, and it is safe precisely because it is bounded.

Phase 4 Prerequisites

Phase 4 is data and API design: the PostgreSQL schema, entity-relationship model, migration strategy, API architecture and endpoints, request and response contracts, authentication and authorisation models, webhook architecture, event schemas, queue architecture, caching and vector storage. It is the most self-contained phase so far — the screens and the architecture between them determine most of it.
